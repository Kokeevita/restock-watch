# 재입고 감시

캠핑문 도매몰(campingmoon.co.kr)의 손님 화면만 읽는다. '품절 → 살 수 있음'으로 바뀐 상품과 옵션을 기록하고, 스킨이 읽을 결과 파일을 만든다. 상품이 '판매 → 품절'이 된 때도 적어 품절 상품 화면을 날짜별로 묶게 한다(11/12~).

- 직원이 할 일은 없다. 지금처럼 들어오면 재고를 0에서 1000으로 바꾸는 것이 신호다.
- 로그인·저장·장바구니는 하지 않는다. 카페24에 아무것도 쓰지 않는다.

## 파일

| 파일 | 내용 |
|---|---|
| `restock_watch.py` | 감시 프로그램(파이썬 기본 기능만 씀) |
| `state/snapshot.json` | 지난번 상태(상품: 판매·품절·단종, 옵션 상품: 옵션마다 살 수 있는지) |
| `state/history.json` | 재입고 기록(30일) |
| `state/log.txt` | 실행할 때마다 한 줄 |
| `docs/restock.json` | 스킨이 읽는 결과. 지금 살 수 있는 재입고만, 최신순 |
| `state/soldout.json` | 품절 시각. 상품마다 '판매 → 품절'이 된 때, 감시 전부터 품절이면 `before` |
| `docs/soldout.json` | 스킨(품절 상품 화면)이 읽는 품절 날짜. 지금 품절인 상품만 |
| `docs/shipfee.json` | 스킨(휴대폰 카드 무료배송 표시)이 읽는 배송비 예외. PC 목록 카드의 '배송비' 글이 가장 흔한 값(`common`)과 다른 상품만 `{상품번호: 글}`(11/13) |
| `state/skip.json` | 목록을 못 읽어 버린 실행이 몇 번 이어졌는지. 정상 실행에서 지운다(11/14) |
| `.github/workflows/watch.yml` | GitHub 무료 자동 실행(하루 종일 매시 23분) |

## 결과 파일 주소(스킨이 읽는 곳)

`https://raw.githubusercontent.com/Kokeevita/restock-watch/main/docs/restock.json` — 누구나 읽을 수 있고, 바뀐 내용은 5분 안에 반영된다.

품절 날짜: `https://raw.githubusercontent.com/Kokeevita/restock-watch/main/docs/soldout.json`

배송비 예외: `https://raw.githubusercontent.com/Kokeevita/restock-watch/main/docs/shipfee.json` — 휴대폰 카드 틀은 판매가 · 할인판매가 두 칸만 받아 배송비를 몰라, 개별 배송비 상품(예: 4,000원)에 무료배송이 잘못 붙지 않게 이것으로 본다. 카페24 상품정보 표시설정의 PC 상품목록 '배송비' 항목을 끄면 빈 목록이 된다

```json
{"updated": "2026-11-12T16:58+09:00", "start": "2026-11-10T18:23+09:00",
 "items": [{"p": 4240, "t": "2026-11-12T16:48+09:00"}], "before": [4475, 4468]}
```

- `items`: 품절된 때를 아는 상품(최신순). `t` = 알아챈 시각(품절 뒤 보통 1~2시간 안)
- `before`: 감시를 시작한 `start` 전부터 품절이던 상품(날짜 모름)
- 다시 판매·단종이 되면 빠진다. 또 품절이 되면 새 시각으로 다시 들어간다. 목록에서 잠깐 빠진(숨김) 상품은 기록을 지우지 않는다.
- 처음 채운 값(11/12): 11/10 18:23부터 1시간마다 쌓인 상태 기록을 처음부터 다시 훑어 같은 규칙으로 만들었다.

## 결과 파일 모양

```json
{"updated": "2026-11-12T10:05+09:00", "badge_days": 14, "keep_days": 30,
 "items": [{"p": 4305, "t": "2026-11-12T10:05+09:00", "k": "p", "o": [], "n": "상품명"}]}
```

| 칸 | 뜻 |
|---|---|
| `p` | 상품번호 |
| `t` | 알아챈 시각. 보통 직원이 바꾼 뒤 1시간 안이고, GitHub 정시 실행이 늦으면 2시간 안 |
| `k` | `p` = 상품 전체 재입고, `o` = 옵션 재입고 |
| `o` | 다시 들어온 옵션 이름. 상품 전체가 다 들어왔으면 빈 목록 |

## 안전장치

- 목록이 지난번의 90%보다 적게 읽히면(사이트 오류·차단) 그 실행은 버린다. 상태를 바꾸지 않으므로 거짓 재입고가 나오지 않는다.
- 버린 실행이 1·2번째면 정상으로 끝내고(기록 줄에 '버림 n번째 연속'), 3번째로 이어질 때부터 실패로 끝낸다 → 그때만 GitHub 실패 메일이 간다(11/14 사용자 결정 — 한 번은 다음 실행이 따라잡는다). 11/10~11/14 76번 중 버린 실행은 11/12 03:18 한 번(바로 다음 정상).
- GitHub에서 돌 때는 시작하면서 저장소 최신 커밋으로 옮긴다. 이 실행이 시작한 커밋 뒤에 다른 실행이 기록을 올렸으면(프로그램을 올린 실행 · 줄 선 실행) 옛 기록으로 계산해 '결과 저장'에서 부딪혔다(11/13 18:27). 옮기면 기록 줄 끝에 '최신 기록 ○○에서 시작'.
- 상세를 못 읽은 상품은 지난번 옵션 상태를 그대로 둔다.
- 첫 실행이 기준점이다. 그 전의 재입고는 없다.

## 언제 무엇을 읽나

- 상품 전체가 다시 들어온 것: 실행할 때마다 잡는다(목록 2개만 읽어 1분 안).
- 옵션 하나만 다시 들어온 것: 9~11시, 12~14시, 15~17시, 18~20시 칸마다 그 칸에서 처음 도는 실행이 판매 중 옵션 상품을 모두 읽는다(약 260개, 3~8분). 마친 칸은 `state/snapshot.json`의 `opt_slot`에 적는다.
- GitHub 정시 실행(매시 23분)은 수십 분 늦게 돌 때가 많다. 11/10 밤에는 7분, 48분, 51분 늦었다. 정해진 '시각'에 옵션을 읽게 하면 그 시각을 건너뛸 수 있어서 '칸'으로 정했다.
- `.github/workflows/watch.yml`의 일정 줄은 되도록 고치지 않는다. 열쇠(deploy key)로 일정을 바꿔 올리면 정시 실행이 다시 멈출 수 있다. 바꿔야 하면 사용자가 Actions에서 Disable/Enable을 다시 누른다.
